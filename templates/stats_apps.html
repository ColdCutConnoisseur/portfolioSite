About

This began as a simple script that would fetch live stats for NCAA basketball games during this year's March Madness tournament and try to pace out the final points to be scored by each time. At first, the script just used simple moving averages, but by the end of the tournament this had turned into a full fledged machine learning model and workflow.

The end product was a regression model calculated from observations from all games played within the 2024-25 Season.

Pacer App Overview

The first instance of this script effectively worked as a feed, pulling update text from espn.com, and pacing out remaining points to be scored by each team based on their current pace. The above screenshot shows the next iteration--one in which random forest regressions were implemented to create models to predict 3-pointers, field goals, and free throws separately.

Evolution to Shot Models & Pregame Predictions

Here is the multimodel output for a predication made pregame. If the model is accurate, it shows an opportunity because the app's predicted line differs from the sportsbook line pretty significantly (a 20-point difference!).

Moving Back to a Single Model Predictor & Stats Dict

Here's a screenshot of the live feed after the predictor moved back to a single model. You can see in the terminal window the current stats dictionaries being kept for each team. These stats dictionaries are held and updated everytime that the feed receives a new game update, e.g. a field goal attempt. And on every update the revised dictionary is fed to the model and a resulting point prediction is printed.

Buildout of the Current Model

I got to the point where I was interested in having a model built from observations from the entire season. This is opposed to the original models being built from only recent observations occurring within the tournament. Here's the workflow that I used to create the new model: First, I created a game day dictionary. It was effectively a mapping of event_ids for all games played within the 2024-25 season. I used the above espn calendar to find all games and their respective event_ids (event_ids were found in the underlying html and could be used to visit the related play-by-play page).

Building Observations

I then had another script that would take the event_id mapping and visit each of the play-by-play pages for that game. The script would walk through all game updates within the play-by-play table for each half and create an observation at each point in time that a game update occured, reflecting the current stats of the specific team, for that specific game, at that specific point in time. In the terminal printout above, you can see the printout of each handled game update and the respective final stats dictionaries that result after all game updates are handled. This is an illustration of what is basically recorded at the occurrance of each game update (the dictionary at that point in time).

Problems Faced

A reoccurring problem I faced was being able to accurately differentiate which game update belonged to which team. From the previous screenshots, it looks like this logic would be simple, but the underlying html did not carry any info on which update belonged to which team. Initially all methods of telling which game update belonged to which team was done through inference. For example, one of the earliest ways I was parsing game updates was through looking at 'Jump Ball' text and who won the jump ball. It might be an update saying, "Purdue won Jump Ball", and I could then carry the respective logo url as an identifier for Purdue updates. This broke down in the overall workflow when I began grabbing data from further back in the season, where not every game was providing jump ball text. 'Home' versus 'Away' text could be used on a game-by-game basis, but there wasn't really anything reliable to consistently identify who home and away was especially during tournament time. The solution was to visit a separate espn stats table, showing season stats for all teams (complete with their logos), and to map each team to the respective logo url that espn.com was using. I then kept this data for update lookups in the above table. Basically on each game update, I'd look at the repsective team logo printed on the update line, get its url, and then find this url within my table, which would tell me the name of the team that specific update belonged to.

Binning Stats

Through some trial and error, I got to the point where I decided that binning the stats within 30 second timeframes was the most effective in working for my specific usecase--one in which I wanted a prediction for the final score as a function of how much time was remaining within the game (think betting live point totals). The above table shows the results of iterating each game played by each team and binning stats for each team (I found this was a better predictor than just using the plain old season stats).

For example, looking at the topmost entry within the database table. Those stats, for the team with an ID of 1, would average 10 three-pointers, 20 field goals, and 17 free throws. This is because that record is for 0-30 seconds remaining in the game (speaking bin-wise). Now just to further illustrate, if you look at something like record 14, that's effectively saying that team with ID of 1 usually has 9.3 three-pointers made, 17 field goals made, and 12.5 free throws made when there is 390 to 420 seconds remaining in the game. Each of these individual observations at different points in time allow the model to tell whether a team is behind, at, or in front of their average in-game production.

Feature Importances

As part of model selection I was typically looking at how each model produced was influenced by its variables. Here's a look at the feature importance breakdown. I don't think that this was the FI of the final model used (because it still uses 'average points' and I moved away from this in favor of binned stats), but it still illustrates some of the more influential variables.

This model also introduced the idea of weighting or magnifying the variables so that certain ones carried more influence. Further models introduced negative multiples to reflect stats that would hurt the final prediction, for example turnovers.

About

This is a relative value setup for pricing shares of Coinbase stock provided current market context, such as the price of gold, cryptocurrencies, and equity index futures. It attempts to take advantage of price discrepencies between the current market and what the model suggests is the 'appropriate' value. When a large enough residual, or difference between the two prices exist, the goal is to either short or long Coinbase stock and take an opposing hedge position in BTC. These positions are held until the predicted and actual value converge or a stop loss is reached.

Overview

Here's a chart of the price of Coinbase stock going all the way back to the last quarter of 2022. The solid blue series is the price of Coinbase stock and the orange, dashed series represents the regression model's prediction of where the price of Coinbase stock should be given details about the current, broader market.

Visualization of a Setup

Here's a zoomed-in view of the previous chart showing an existing trade setup. Basically the price difference between the model (orange) and reality (blue) have diverged by a substantial amount. This is a setup to short COIN and Buy BTC as a hedge. Effectively, Coinbase is overvalued at these levels given the current market context. The +BTC hedge is to guard against a large upswing in BTC price, taking COIN further up with it (The two are heavily correlated because Coinbase's revenue is very correlated with BTC performance).
