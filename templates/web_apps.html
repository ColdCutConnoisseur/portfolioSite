About

This is a web app that I'm currently working on. The app is primarily a dashboard that shows open ticket inventories and periodically polls curret market prices for comparable sections and seating from various marketplace sites. It's primary purpose is to show the user open inventories/exposure and current price trends to better manage the sales of tickets for sporting events, concerts, standup comedy shows, etc.

Change to a Tabbed Interface

After seeing the amount of data to be displayed, I elected to use a tabbed interface instead. There currently exist four tabs: closed inventory, open inventory, watchlist, and an editor tab. These are visible at the top of the screenshot.
The watchlist page will host functionality for watching events in which tickets have not yet been purchased for but the user may have interest in purchasing. The editor tab will eventually act as an interface to the CRUD operations of the 'inventory' table, so that inventory items and watchlist items can be updated (these pages are not built out yet). Inventory items are currently added programatically behind the scenes.

Starting to Fetch Price DataPoints

Here is a view of the ticket marketplace listings and the respective terminal output after checking prices. The script checks all ticket prices for the appropriate section & row and then returns a configured price point and a supply number. I currently have a check where observations are only added at a maximum of once per day; this is to help keep observation numbers down, and was done in hopes of creating a time series that would be more telling of price trends over time.
Configured price points may be something like the minimum price offered, the max price, the median price, the average of the lowest three ticket prices, etc. and this is configured within the app. In this screenshot, the script is computing the average of the three lowest ticket prices.
The supply element or 'section_inventory_count' (seen above as the '32 listings found' line) is a datapoint that I just added in the 'prices' table of the database. This count was readily available and I figured it could be a beneficial datapoint to track for the end user. It should assist in providing data around whether there exists true demand / low supply for an event or whether the market is swamped with inventory from scalpers / resellers, etc.

About

This was a commissioned piece of software. Personal Seat Licenses are licenses that are bought and sold on marketplaces, and which entitle the licensee to purchase season tickets for NFL teams.

Why this software exists: for any given team, there may be something like 500 licenses available for sale at any given point in time. My client wanted a tool that would easily differentiate any new listings from existing listings, & the client also wanted the added ability to be notified of listings in realtime and the ability to further filter any new license listings to specified criteria (e.g. meeting a specific price range for a particular section).

PSL Marketplace Example

Here's an example of the license marketplace for the Minnesota Vikings.

Team Configuration

The user sets the configuration file for each NFL team they'd like to track PSLs for. The configuration file maps each team to a marketplace URL. Under the hood, the app will create a headless browser, and for each of the configured URL mappings, the browser will visit each of those websites. The app will then find current license listings and compare those to the ones already existing in the database for that specific team. If new license listings are found and they meet any further specified or configured criteria, the end user receives a message through Telegram.

What I Used:

  • pythonanywhere.com for hosting the code & database and for task scheduling
  • selenium for running a browser and interacting with web elements
  • telegram-python the python telegram client for creating and running a bot server

What I Learned:

Although a simple app, I had most difficulty with the loading of marketplace webpages. For some reason they are just really slow web pages (maybe because they are .aspx). This resulted in additional code that would either have to assert a successful marketplace load, or in the event of an unsuccessful load, that all of the existing database entries for that specific team's tickets were not deleted from the database --> basically a page would not load, the app would read this as that team not having any tickets for sale (no listing elements found), and then the app would delete all existing database entries because it assumed that all of those listings were delisted. On the next update and successful page load, the app would then send like 500 messages for each listing thinking that all of these listings were new (empty database table).

I also had to determine the most efficient task schedule in order to not exceed the amount of compute time that the client was willing to pay for. This tool was also a good refresher on Telegram bot messaging and error catching / waits in selenium.
